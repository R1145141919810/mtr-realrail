# 04 · 潜在风险与兼容性说明

## 1. 与 MTR 版本的兼容性

### 1.1 版本矩阵（MC 1.20.1 线）

| MTR 版本 | 发布日期 | 兼容性 | 说明 |
|---|---|---|---|
| 4.0.0-beta.8 ~ beta.16、prerelease.1 | 2024-06 ~ 2025-04 | ❌ **不支持** | 该时期 TSC 使用 `simulateAutomaticMoving`/`getRailSpeed`，无 `simulateMoving` 与 `Siding.getUpcomingSlowerSpeed`（2025-05 才引入），本 mod 的 Mixin 目标不存在 |
| 4.0.0-prerelease.2/3 | 2025-05 / 2025-06 | ⚠️ 可能支持 | `simulateMoving` 已引入（"Manual driving changes" e8c4b43 / "Vehicle simulation refactoring" eb3b331），未逐一验证 |
| **4.0.0（正式）~ 4.0.1** | 2025-07 / 2025-08 | ✅ 预期兼容（最低支持版本） | 与 4.0.2–4.0.5 同线；建议冒烟验证 |
| **4.0.2 ~ 4.0.5** | 2025-10 ~ 2026-06 | ✅ **验证基准** | 复用同一内嵌 TSC jar（mod 仓库 libs 最后更新 2025-10-14，对应 TSC commit `599d1076`）；Mixin 目标已逐行核对 |
| 4.0.6 分支（源码）/ 未来发行版 | — | ❌ 不保证 | 该分支已把核心抽取为 `libs/Transport-Simulation-Core-0.0.1.jar` 且主仓面向 1.20.4；TSC master 已引入 "basic/advanced 信号"（alpha 位）拆分（2026-06-18，晚于 4.0.5） |

### 1.2 未来版本风险点

1. **TSC "basic/advanced 信号"**：TSC master 的 `Vehicle.checkAndBlockSignal` 新增 `hasAlpha = (color & 0xFF000000) != 0` 分支（advanced 模式要求区间出口 lookahead）。本模组不触碰该方法，若未来发行版合并该改动，需回归验证隔离语义是否与 alpha 位交互（预计无冲突，但必须实测）。
2. **包结构再迁移**：主仓库已将 mod 层包改为 `org.mtr.mod.*`（2023-09 起）并持续重构；若未来再次调整 `org.mtr.core.*` 类名/签名，两个 mixin 的目标与 shadow 需同步更新（编译期即可发现）。
3. **MTR 5 / 主版本**：4.0.6 分支显示核心已外置为独立构件，未来发行版若改变 `Vehicle.simulateMoving` 的限速读取方式（例如引入原生车尾判定），本模组应降级为仅提供 GUI 层或直接退役。

### 1.3 多 MC 版本

本脚手架为单版本（MC 1.20.1）。若需 1.20.4/1.21 等版本：升级 Forge/Architectury 版本并重验（MC 层接口变化不影响 mixin 目标，因目标全在 `org.mtr.core`——TSC 与 MC 版本解耦，这是选择 core 层注入的关键收益）。

## 2. 与其他 MTR 附属模组的冲突风险

| 模组 | 风险 | 说明 |
|---|---|---|
| **JCM（Joban Client Mod）** | 低 | JCM 为客户端设施模组 + JS 渲染 API，不 mixin `org.mtr.core` 服务端仿真逻辑；信号渲染仍走 `SignalBlockUpdate` 数据流，隔离后状态正确 |
| **NTE（Nemo's Transit Expansion）** | 低 | NTE 主要为渲染/扩展车辆；其 1.20.1 目标实际是 MTR 3.2.2（`mtr.*` 旧口径），与本模组目标版本线不同，无共同运行时 |
| 其他 mixin 服务端仿真的 addon | **中** | 若第三方同样 `@Inject/@Redirect` `Vehicle.simulateMoving`/`Rail.isBlocked`：Mixin 注入点不同时互不干扰；**相同注入点**存在顺序依赖（如同时 redirect 同一 INVOKE 会互相覆盖语义）。建议发布前与已知 addon 组合冒烟测试 |
| MTR 自带的轨道界面（`RailModifierScreen`） | 低（已按"共存"实现） | MTR 4.0.x 的 `BlockNode.onUse2` 在客户端用刷子右键打开轨道形状/样式界面。本模组**不再接管该交互**：原版界面与全部原版功能保持不变，本模组只在该界面 `init2()` 尾部追加一个"节点限速判定"按钮（`RailModifierScreenMixin`，字符串 targets + 独立非必需 mixin 配置）。若未来 MTR 改动该界面类名或 `init2()`，按钮会静默缺失并记录日志，不影响游戏与其他功能 |
| 修改 mtr:brush 行为/替换其注册名的资源包/模组 | 低 | 本模组按注册表名 `mtr:brush` 匹配；被替换时 GUI 不触发（不崩溃），改常量即可适配 |

## 3. 实现层面的已知风险与边界

1. **TAIL 判定的物理后果**：车头先进入更慢的段而车尾未通过时，列车保持原速度 → 进入慢区后才开始减速，存在**冲入慢区的过冲**。这是需求一"延迟变更"的固有语义（真实铁路为"限速点前减速、车尾清限速后加速"，与任务书要求的"双向延迟"不同）。缓解：a) `getUpcomingSlowerSpeed` 对 HEAD 判定节点仍保留预制动；b) 信号/平台/前方占用仍立即制动（安全不受影响）；c) 可后续增加"按车身覆盖段取最小限速"的可选模式。
2. **节点模式键的维度粒度**：`NodeModeStore` 以 "x,y,z" 为键（与 MTR `positionsToRail` 一致）。MTR 4.0.x 每个 `Data/Simulator` 实例对应一个世界维度场景；**若同一存档多维度存在同坐标铁路且期望不同配置，会共享同一模式**。MTR 本体同样以 Position 全局索引轨道，此限制与其一致；跨维度地铁场景极少，作为已知限制记录。
3. **信号隔离的语义代价**：系统 A 的列车占用带双色连接器的轨道时不再占用系统 B 的区间——若现实中两系统列车确实共用同一轨道，B 系统列车将看不到 A 列车的占线（B 区间"无人占用"）。这是任务书要求"互不干扰"的必然结果；物理重叠检测仍然防撞（两车不会相撞，但 B 车可能被物理检测拦停而非信号拦停）。对"严格分离的两套系统共用路网"的场景无影响；对"混合运行"场景建议信号上仍用单一颜色。
4. **注册表 TTL**：信号归属注册每 tick 刷新、10s 过期。列车移除后最长 10s 内该 id 的回退为原版逻辑（仅当同 id 被复用时可能短暂出现——MTR 车辆 id 为递增 long，实际不复用）。
5. **配置重载**：`config/mtrrealrail.properties` 在服务端启动时读取；运行中修改需重启（与 MTR 自身 config 行为一致）。
6. **性能**：每 tick 每车新增 O(车身覆盖段数) 的颜色并集计算（通常 ≤ 数个段）+ 状态机 O(1)；`Rail.isBlocked` 过滤为 O(颜色数 ≤ 16)。开销可忽略；`ConcurrentHashMap` 保证线程安全（TSC 在服务端线程模拟）。

## 5. 适配指南（升级 MTR 版本时）

1. `gradlew :forge:build`：mixin 目标缺失 → 编译失败即知。
2. 运行参数 `-Dmixin.debug.verbose=true -Dmixin.debug.export=true`：核对 `Mixin apply for mod mtrrealrail ... SUCCESS` 与导出源码中的注入位置。
3. 对照新版 jar：反编译 `org.mtr.core.data.Vehicle#simulateMoving`（找 `getSpeedLimitMetersPerMillisecond` 与 `getUpcomingSlowerSpeed` 调用）、`Rail#isBlocked/reserveRail`，并核对 `Vehicle.simulate` 第三参数类型（发行版 4.0.2–4.0.5 为 `Long2LongAVLTreeMap`；若升级为 `Long2ObjectOpenHashMap` 需同步改 `@Inject` 参数）。
4. 若限速读取点变化：把 `@Redirect` 目标更新为新调用，`SpeedLimitHelper` 通常无需改动。
5. 若信号数据结构变化（如 basic/advanced 拆分）：更新 `RailSignalIsolationMixin` 的颜色过滤语义并实测双色场景。
