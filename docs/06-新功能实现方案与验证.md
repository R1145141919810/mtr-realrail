# 06 · 新功能实现方案（动态轨道占用 / 自动最优路径规划 / 动态发车避让 + 车厂 GUI）

本文对应"新增功能"需求，说明**实现方案、与 MTR 的交互方式、数据结构与算法、关键代码位置、
GUI 表现方式、测试验证方法与兼容性建议**。原有功能（docs/01、docs/02 的需求一/需求二）保持不变，
所有新功能都可通过配置单独关闭。

---

## 1. 总体思路

MTR 4.0.x 的列车仿真完全在服务端核心 TSC（随 MTR 发行的 `org.mtr.core`）中进行：

- 每 tick：`Simulator.tick()` → `Siding.simulateTrain()` → `Vehicle.simulate()`；
- 列车位置是沿路径的一维距离 `railProgress`，路径 `vehicleExtraData.immutablePath`（**final，不可替换**）；
- 闭塞由"同色连通轨道分量"隐式表达：`Rail` 内四张 `颜色 → 车辆 id` 表，`reserveRail` 沿共享端点 DFS 预留；
- 停站时长由 `VehicleSchema.elapsedDwellTime` 与站台段 `PathData.dwellTime` 驱动，达到"关门时刻"
  且前方畅通即发车。

因此本模组**不重写 MTR 的仿真与寻路**，而是：

| 新功能 | 实现方式 | 落到 MTR 的哪个机制 |
|---|---|---|
| 动态轨道占用 | 每 tick 从 `Vehicle.simulate` 抓取"车头/车尾在每条轨道上的真实覆盖区间"，建立独立索引；作为固定闭塞的补充 | 读 `PathData.getRail()/getSignalColors()/getStartDistance()/getEndDistance()/getRailLength()` |
| 移动闭塞放行 | 固定闭塞判"占用"时，用真实间距（制动距离 + 安全间距）决定是否放行；放行时**不抢占前车预留** | 注入 `Rail.isBlocked`（与需求二的信号隔离同一入口） |
| 自动最优路径规划 | 用实时占用与 ETA 对进路打分；发车时序优化；必要时调用 MTR 自身的路径生成入口重新生成车厂路径 | 读 `Data/Simulator`、`Route`、`Depot`；写 `Simulator.run(...)` + `Depot.generateDepots(...)` |
| 动态发车与避让 | 停站满阈值后进行"立即发车 vs 等待让行"的代价比较；等待时压住停站计时 | 注入 `Vehicle.simulateStopped`，写 `VehicleSchema.elapsedDwellTime` |
| 车厂 GUI | 在 MTR 车厂配置界面追加"优化线路配置"按钮，打开本模组界面 | 客户端 mixin `EditDepotScreen.init2` + 原版控件 API |

**明确不做的事**：不替换 `immutablePath`（final）、不重写 `PathFinder`、不改动
`railBlockedDistance`（物理防撞）与 stoppingPoint 安全制动分支。这样既拿到了新能力，
又保证"不破坏现有框架及原本功能"。

## 3. 数据结构与算法

### 3.1 动态轨道占用（轨道局部坐标区间）

每 tick 对每辆车：沿车尾到车头的路径段，把 `[车尾, 车头]` 与每段 `[startDistance, endDistance]` 求交，
再换算成**轨道局部坐标**（米）；反向行驶的段翻转坐标：

```java
final double from = Math.max(pathData.getStartDistance(), snapshot.tailProgress());
final double to   = Math.min(pathData.getEndDistance(),   snapshot.railProgress);
double localA = from - pathData.getStartDistance();
double localB = to   - pathData.getStartDistance();
if (pathData.reversePositions) {           // 轨道局部坐标与行驶方向相反
    final double flippedA = railLength - localB;
    localB = railLength - localA;
    localA = flippedA;
}
railOccupancy.computeIfAbsent(pathData.getRail().getHexId(), k -> new ArrayList<>())
        .add(new Interval(vehicleId, localA, localB, speed, pathData.getSignalColors().toIntArray()));
```

于是得到 `轨道 → 若干占用区间（含速度与信号颜色）` 的索引。查询全部 O(段数)，与 MTR 的
"整条同色连通分量二值占用"相比，粒度细化到**米级 + 速度**。

### 3.2 信号辅助的冲突判定

**两条占用区间只有共享至少一种信号颜色时才算冲突**（与需求二"多信号系统互不干扰"一致）：

```java
public static boolean sharesColor(int[] a, int[] b) {
    for (final int colorA : a) for (final int colorB : b) if (colorA == colorB) return true;
    return false;
}
```

无信号颜色的轨道视为"不属于任何信号系统"，按物理安全处理（不参与放行判定）。
这正是"通过信号系统（信号线）辅助优化"的落点：**信号颜色既是隔离边界，也是冲突检测与
进路打分的分组键**——同一信号系统内的列车才互相影响，跨系统互不干扰。

### 3.3 移动闭塞放行（动态轨道占用 → 轨道资源精细分配）

固定闭塞（MTR 的 `isBlocked`）只有"占用/空闲"，本模组补充：

```java
private static boolean mtrrealrail$dynamicRelease(long vehicleId) {
    final VehicleSnapshot self = TrafficRegistry.get(vehicleId);
    if (self == null) return false;
    final OptimizeSettings settings = DepotSettingsResolver.settingsForVehicle(vehicleId);
    if (!settings.dynamicBlockRelease) return false;

    final DynamicOccupancy.Leader leader = DynamicOccupancy.findLeaderAhead(
            self, Math.max(settings.pathLookaheadMeters, settings.safetyMarginMeters * 4));
    if (leader == null) return false;                     // 前方没有同信号系统列车 → 保守不放行

    return leader.distanceMeters() >= self.brakingDistance() + settings.safetyMarginMeters;
}
```

放行时返回"不占用"且**不调用 reserveRail**，因此前车的预留不会被覆盖（否则前车会被反判为
"被其它车占用"而停车）。信号灯显示仍由前车的预留决定（红），显示正确。

### 3.4 进路打分与 ETA

```java
// 前方 lookahead 米内被"同信号系统"车辆占用的长度比例
double ratio = DynamicOccupancy.occupancyRatioAhead(self, lookahead);
// 折算成预计延误：占用比例 × 前瞻长度 ÷ 期望速度
long delay = (long) (ratio * lookahead / Math.max(speedLimitAt(self), 1e-5));
// ETA：速度过低时按"限速的一半"保守估计
long eta = (long) Math.ceil(distance / Math.max(speed, Math.max(1e-5, limit * 0.5)));
```

### 3.5 发车决策代价函数（任务中的 A/B 场景）

```
本车立即发车代价 = 前方拥挤延误 + (前方同信号系统列车将在冲突窗口内到达 ? 进入占用区间罚分 5000ms : 0)
本车等待让行代价 = 已等待时间   + (后方列车将在冲突窗口内到达本站台 ? 长时间占用站台罚分 7500ms : 0)
代价小者胜；等待超过 maxHoldSeconds → 强制发车（并可触发车厂路径重新生成）
```

对任务场景（A 到站、B 将在 5 秒后到站、A 停站满 10 秒）的推演：

| 情况 | 发车代价 | 等待代价 | 决策 |
|---|---|---|---|
| A 前方区间空闲，B 5 秒后到站 | 0 | 7500 ms（挡住站台） | **立即发车**，把站台让给 B |
| A 前方同信号区间 5 秒内将有车进入 | 5000 ms | 0~等待时长 | **等待避让**，不进入即将被占用的区间 |
| 等待超过 maxHoldSeconds（默认 60 s） | — | — | **强制发车** + 调用 `Depot.generateDepots` 重新生成路径（变更路径） |

"等待"的执行端（`Vehicle.simulateStopped` RETURN 注入）：

```java
final long doorCloseTime = Math.max(totalDwellMillis / 2, totalDwellMillis - 3200L - 1000L);
if (accessor.mtrrealrail$getElapsedDwellTime() >= doorCloseTime) {
    accessor.mtrrealrail$setElapsedDwellTime(Math.max(0, doorCloseTime - 1));  // 压住发车
}
```

即：把停站计时压在"关门时刻"之前，MTR 就不会触发 `startUp`（发车）；列车保持开门等待，
直到决策改变。放行时不再写该字段，MTR 恢复原版发车流程。

## 4. GUI 表现方式（铁路仪表板 → 车厂配置）

实现链路（沿用本模组已有的"映射层控件"做法，见 `RailModifierScreenMixin`）：

```
铁路仪表板 → 车厂 → 点击某个车厂 → MTR 车厂配置界面（org.mtr.mod.screen.EditDepotScreen）
    └─ EditDepotScreenMixin（@Inject init2 TAIL，客户端、required=false 配置）
         ├─ 反射读取该界面的 Depot 字段（读不到只记日志，绝不影响原版界面）
         └─ 用 MTR 自身控件追加按钮「优化线路配置」：
              ButtonWidgetExtension + ScreenExtension.addChild + IDrawing.setPositionAndWidth
              位置 = 右栏（x=rightPanelsX，宽=屏宽-rightPanelsX），
                     y = MTR"本车厂的侧线数目"文字行 + 15px —— 正好落在该行与下方
                         "xx 分钟前刷新路径"信息块之间的空档（MTR 的文字块间距为 40px）
              └─ 点击：记住车厂界面 → 立即打开 DepotOptimizeScreen → 同时请求服务端配置刷新
```

**键盘入口**：另注册快捷键 **O**（{@code key.mtrrealrail.optimize}）。
{@code ScreenEvent.KeyPressed.Pre} 在界面收到按键前触发，因此在车厂界面里按 O 可直接打开本界面；
正在输入文本（焦点在输入框）时不拦截。界面打开时若没有任何控件获得焦点，会把焦点给该按钮，
此时直接按回车也能打开。

### 4.2 已修复的严重缺陷：列车被无限期压在站台（v1.1.1）

**现象**：列车停在站台、车门一直不关、始终不发车（即使前方区间实际没有列车），后方列车被堵。

**根因（两处叠加）**：

1. `DynamicOccupancy.findLeaderAhead` 的"前方最近障碍"计算有误：区间映射后若整段都落在**车头之后**
   （例如紧跟在本车后面的那列车），距离被钳位成 0，于是**后车被判成"0 米处的前车"** →
   `hasConflictAhead` 恒为真 → 发车代价恒大于等待代价 → 一直判定"等待避让"。
2. ```java
   // 旧实现：把停站计时压在"关门时刻"之前
   accessor.mtrrealrail$setElapsedDwellTime(Math.max(0, doorCloseTime - 1));
   ```
   该值落在 MTR `simulateStopped` 的**开门分支**区间 `[DOOR_DELAY, doorCloseTime)` 内，
   因此每 tick 都会重新开门、且永远不满足发车条件 → 表现为"车门一直不关、车不走"。
   旧版还有"等待超时后立刻重新压站"的抖动，以及等待计时使用游戏内时钟（伺服/暂停时不推进）的风险。

**修复**：

| 项 | 修复内容 |
|---|---|
| 前车判定 | 严格区分前后：只有"部分/完全位于车头前方"的占用才算前车（`range[1] <= railProgress` 直接跳过）；后车判定同理（`range[0] >= tail` 跳过） |
| 冲突判据 | 从"用前车速度推算 ETA"改为**间距判据**：`间距 < 本车制动距离 + 安全间距` 才算冲突（前车同向驶离时不再误判） |
| 决策表 | 改为显式规则：①前方无冲突 → 立即发车；②前方有冲突但后车逼近 → 发车让出站台；③刚释放过（20 秒冷却）→ 直接发车；④其余情况才等待避让，且**最长 15 秒**（原 60 秒）后强制发车 |
| 计时 | 等待计时改用**墙钟**（`System.currentTimeMillis()`），与游戏内时钟解耦，超时必定生效 |
| 观察性 | 开始等待/超时强制发车时以 INFO 输出一行摘要（含前后车距离、速度、占用比例），便于服主定位；同车 30 秒节流 |
| 看不见的占线 | 动态闭塞放行新增兜底：**前方根本没有同信号系统列车**时，说明该闭塞的占用不来自本车前方（后方/分歧/异常预留），允许进入且不抢占预留，由 MTR 的物理防撞兜底——避免被"看不见的占线"永久卡死 |

> 另：`optimize_max_hold_seconds` 默认值由 60 改为 **15**；若仍希望完全关闭发车干预，
> 可在车厂界面关闭"动态发车与避让"或设置 `optimize_departure_guard=false`。

### 4.3 已修复：车厂优化配置读取失败（v1.1.2）

**现象**（服务器日志）：

```
WARN [MTR RealRail] [mtrrealrail] 读取车厂优化配置失败：For input string: "安全间距"
```

**根因**：写出端为了让玩家看懂格式，第一行写了带 `|` 的表头注释：

```
# 车厂 id|动态闭塞|安全间距|路径优化|前瞻距离|发车避让|停站阈值(s)|冲突窗口(s)|最长等待(s)
```

读取端却按 `|` 切分**所有**非空行，于是该注释行也被切成了 9 段、恰好通过了"字段数 = 9"的长度检查，
随后 `Double.parseDouble("安全间距")` 抛异常；而异常是在整个循环外层捕获的，
**导致整份文件被放弃**——所有车厂的单独配置在服务器重启后静默丢失（回落到全局默认）。

**修复**：

| 项 | 修复内容 |
|---|---|
| 注释/空行 | 读取时跳过以 `#` 开头的行与空行 |
| 单行容错 | 每行单独 try/catch，损坏行只跳过该行，不影响其它车厂配置 |
| 可观测性 | 读取结束输出 INFO：`车厂优化配置读取完成：成功 N 条，跳过 M 行（文件路径）`；有跳过行时另给 WARN |
| 写出 | 表头改为更明确的注释说明；条目按车厂 id 排序，文件稳定可读 |

**验证**（真实 Forge 服务端，刻意使用旧格式文件 = 带 `|` 表头 + 2 条车厂记录）：

```

界面内容（`DepotOptimizeScreen`）：

- 左列三个开关：动态闭塞放行（移动闭塞） / 自动最优路径规划 / 动态发车与避让；
- 右列五个数值（`-` / `+` 步进）：安全间距、前瞻距离、停站阈值、冲突窗口、最长等待；
- 底部四按钮：**应用** / **应用并刷新路线** / 恢复全局默认 / 返回车厂配置（ESC）；
- 固定提示（黄字）："操作完成后需重新刷新路线：请点击下方\"应用并刷新路线\"，

2. 玩家按提示返回车厂界面点击 MTR 原版"生成路线"按钮（零耦合兜底）。

## 6. 兼容性建议

### 6.1 MTR 版本

| 目标 | 说明 |
|---|---|
| MTR 4.0.0 ~ 4.0.5（1.20.1 线） | **支持**（编译/验证基准 4.0.5）。新功能只依赖 `org.mtr.core` 的公开 API 与三个已核对的字段（`railProgress/speed/elapsedDwellTime`）与 `data` 字段 |
| MTR 4.0.6+ / TSC master | `Vehicle.simulate` 第三参数等签名可能变化（发行版为 `Long2LongAVLTreeMap`，master 已改 `Long2ObjectOpenHashMap`）→ 需按 docs/04 §5 更新 mixin 描述符 |
| MTR 3.x / beta 系列 | 不支持（无 `simulateMoving`/`getUpcomingSlowerSpeed`） |

### 6.2 加载器

- 本项目当前为 **Forge 1.20.1 单平台**（`ForgeGradle 6`）；
- 新功能本身与加载器无关：动态占用/决策层只依赖 `org.mtr.core`（TSC 与 MC 版本解耦），
  只有 GUI 与网络层需要平台适配：
  - 网络：Forge `SimpleChannel` → Fabric 用 `ServerPlayNetworking`/`ClientPlayNetworking`；
  - 事件：Forge `ServerStartedEvent`/mixin → Fabric 用 `ServerLifecycleEvents`；
  - 客户端界面：Forge/原版 `Screen` 与 mixin 注入 MTR 界面的做法在 Fabric 上完全一致（MTR 的映射层
    `ScreenExtension` 两平台通用）；
- 若需要 Architectury 双平台，可把 `RealRailConfig/NodeModeStore/OptimizeConfigStore/traffic 包`
  原样放入 common 模块，仅把网络与生命周期事件换成 Architectury API（docs/01 的原设计）。

### 6.3 与其它附属模组

- 与"也 mixin `Rail.isBlocked` / `Vehicle.simulate`"的模组存在注入点竞争（docs/04 已记录）；
- 新的动态闭塞放行会**改变信号区间内的多车共存**（这正是功能目标）：
  若服务器希望严格一区间一车，请在配置里把 `optimize_dynamic_block_release=false`
  （或在车厂界面关闭"动态闭塞放行"）。

## 7. 已知限制

1. `immutablePath` 为 final，**运行中无法给单个列车换一条完全不同的路径**；因此"变更路径"是通过
   "发车时序 + 车厂路径重新生成"实现的（与 MTR 自身"生成路线"按钮同机制，对后续发车生效）。
2. ETA 采用运动学估算（当前速度 / 限速折半兜底），未做完整牵引曲线建模；对调度决策足够，但不适合做时刻表级预测。
3. 跨维度的车厂/线路 id 在各维度 Simulator 中可能重名，配置以"存档 + 车厂 id"为键（与 MTR 的
   `positionsToRail` 同粒度限制，见 docs/04 §3.2）。
4. 客户端两个界面 mixin 依赖 MTR 的 `init2` 钩子名（映射层自有方法名，非 MC 重写名），
   MTR 大版本升级时若改名需同步调整——配置为 `required=false`，最坏情况只是按钮不出现。
