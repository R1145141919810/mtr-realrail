# 07 · 车站站台智能调度（实现方案与验证）

本文件对应新需求"车站站台智能调度"，说明**实现方案、数据结构、关键代码、与信号系统的结合方式、
测试验证方法与兼容性**。既有功能（限速判定、信号隔离、动态占用/路径规划/发车避让、车厂 GUI）全部保留。

---

## 1. 需求与总体思路

| 需求 | 实现 |
|---|---|
| 车站配置界面：拥有 ≥2 个站台的车站增加"站台智能调度"开关 | {@code EditStationScreenMixin} 在 MTR 车站配置界面追加开关按钮（不足 2 个站台时不显示） |
| 线路配置界面：增加"线路智能调度站台"选项，进入专用 GUI 规定每条线路在每个车站可停靠哪些站台（多选） | {@code EditRouteScreenMixin} 追加按钮 → 打开 {@code RouteDispatchScreen}（按车站分页 + 站台多选 + 应用/应用并刷新路线/ESC 返回） |
| 动态站台分配：列车进站时若原定站台已被占用，自动引导到该车站其它可用且允许的站台 | {@code PlatformDispatcher}（实时站台占用 + 备用站台选择 + 进站等待引导）+ {@code RoutePlatformDataMixin}（把"允许集合"施加到 MTR 的路径生成上） |

设计原则：**只读 + 少量写入 MTR 自身的数据结构**，不改寻路算法、不改物理防撞；所有新行为可通过界面开关关闭。

## 2. 与 MTR 的交互（用到的真实 API）

| 用途 | API（javap 核对 4.0.5 发行 jar） |
|---|---|
| 车站的站台集合 | {@code Station.savedRails}（{@code AreaBase.savedRails}，public） |
| 站台所属车站 | {@code SavedRailBase.area}（{@code Platform.area}，public） |
| 线路站序 | {@code Route.getRoutePlatforms() → ObjectArrayList<RoutePlatformData>}；{@code RoutePlatformData.getPlatform()} / public 字段 {@code platform} |
| 站台-路径对应 | {@code Platform.containsPos(Position)} + {@code PathData.getOrderedPosition1()/2()}（停车段的端点） |
| 停站判定 | {@code PathData.getDwellTime() > 0} 的段即"站台段" |
| 站台-线路缓存 | {@code RoutePlatformData.writePlatformCache(Route, Long2ObjectOpenHashMap<Platform>)}（路径生成前解析站台对象） |
| 路径重新生成 | {@code Depot.generateDepots(Simulator, depots)}（经 {@code RouteRefresher}，与仪表板"生成路线"同一入口） |
| 界面注入 | {@code EditStationScreen} / {@code EditRouteScreen}（均为 {@code EditNameColorScreenBase} 子类）+ {@code ScreenExtension.addChild} + {@code IDrawing.setPositionAndWidth} |

## 3. 数据结构与持久化

{@code world/mtrrealrail/platforms.json}（纯文本、逐行容错）：

```
# station|车站id                       —— 该车站启用站台智能调度
# route|线路id                         —— 该线路启用线路智能调度站台
# allow|线路id|车站id|站台id,站台id…    —— 该线路上该车站允许停靠的站台（多选）
station|123456789
route|987654321
allow|987654321|123456789|-1234567,-2345678
```

由 {@code PlatformDispatchStore} 管理（与服务端一致的三层结构：车站开关 / 线路开关 / 线路×车站允许集合）；
读取跳过注释与空行、单行损坏只跳过该行（沿用 v1.1.2 的容错约定）。
空集合 = 不限制（按 MTR 原版行为 + 占用驱动选择）。

## 4. 关键流程与代码

### 4.1 站台实时占用（信号辅助）

```java
/** 站台是否被其它列车占用：有列车正在该站台停站即为占用。 */
public static boolean isPlatformOccupied(Data data, Platform platform, long excludeVehicleId) {
    for (final VehicleSnapshot snapshot : TrafficRegistry.snapshots()) {
        if (snapshot.vehicleId == excludeVehicleId || !snapshot.isStopped()) continue;
        final PathData pathData = Utilities.getElement(snapshot.path, snapshot.headIndex);
        if (pathData == null || pathData.getDwellTime() <= 0) continue;   // 只有"站台停车段"才算
        final Platform other = findPlatform(data, pathData);              // 端点反查站台
        if (other != null && other.getId() == platform.getId()) return true;
    }
    return false;
}
```

- 列车位置/速度来自既有的 {@code TrafficRegistry}（每 tick 由 {@code VehicleSimulateMixin} 更新）；
- 冲突判定沿用**信号颜色**语义（{@code DynamicOccupancy.sharesColor}）：不同信号系统互不干扰；
- 因此站台占用是"实时 + 按信号系统"的，而不是 MTR 固定闭塞的二值占用。

### 4.2 列车下一个停靠站台

沿列车路径向前找第一段 {@code dwellTime > 0} 的停车段，再用该段端点反查站台：

```java
public static StopInfo nextStop(Data data, VehicleSnapshot self) {
    int index = Math.max(self.headIndex, 0);
    PathData pathData = Utilities.getElement(self.path, index);
    if (pathData == null) return null;
    if (pathData.getDwellTime() <= 0) {                 // 当前不是站台段 → 向前找
        for (index += 1; index < self.path.size(); index++) {
            final PathData candidate = Utilities.getElement(self.path, index);
            if (candidate == null) return null;
            if (candidate.getDwellTime() > 0) { pathData = candidate; break; }
        }
        if (pathData.getDwellTime() <= 0) return null;
    }
    final Platform platform = findPlatform(data, pathData);
    ...
}
```

### 4.3 动态站台分配决策（每 tick 每车）

```
1. 目标站台空闲                       → 不干预
2. 目标站台被占 +（线路,车站）启用调度：
     存在"允许且空闲"的备用站台        → 记录改停决策（路径生成时按允许集合落到备用站台）
     不存在                            → 在尚未进站时压住列车等待（上限 20 秒，绝不死锁）
3. 未启用调度                         → 不干预
```

### 4.4 "允许集合"如何真正改变停靠站台（关键）

MTR 生成路径前会把线路站序里的 platformId 解析成站台对象缓存，路径生成器读这个缓存。
本模组在该方法返回后做一次**约束替换**：

```java
@Mixin(RoutePlatformData.class)
public abstract class RoutePlatformDataMixin {
    @Inject(method = "writePlatformCache", at = @At("RETURN"))
    private void mtrrealrail$applyAllowedPlatform(Route route, Long2ObjectOpenHashMap<Platform> platformIdMap, CallbackInfo ci) {
        final RoutePlatformData self = (RoutePlatformData) (Object) this;
        final Platform current = self.getPlatform();
        if (current == null || current.area == null) return;
        final long routeId = route.getId();
        final long stationId = current.area.getId();
        if (!PlatformDispatchStore.isDispatchActive(routeId, stationId)) return;      // 车站开关 + 线路开关
        final Set<Long> allowed = PlatformDispatchStore.allowedPlatforms(routeId, stationId);
        if (allowed.isEmpty() || allowed.contains(current.getId())) return;           // 未限制 / 本就允许
        for (final long platformId : allowed) {                                        // 换成允许集合内的同车站站台
            final Platform candidate = platformIdMap.get(platformId);
            if (candidate != null && candidate.area != null && candidate.area.getId() == stationId && candidate.isValid()) {
                self.platform = candidate;
                return;
            }
        }
    }
}
```

配合 {@code RouteRefresher.refreshForRoute(...)}（调用 MTR 的 {@code Depot.generateDepots}，界面上的
"应用并刷新路线"按钮）即可让列车按**允许集合内的空闲站台**重新生成进路。

  顶部线路开关；按车站分页（每页 3 个车站），每个车站一行列出该车站全部站台，**按钮多选**（√ = 允许停靠）；
  每站另有"全部/清空"；底部：应用 / 应用并刷新路线 / 返回线路配置（ESC）。

## 4.6 依赖外置调度服务 tsc-dispatch（v1.3.0 起）

"车站站台智能调度"的**决策来源**改为外置调度与动态路径规划服务
[tsc-dispatch 1.0.0](../../tsc-dispatch/README.md)（独立进程，HTTP 交互），本模组只负责
**游戏内执行与界面交互**；原有交互逻辑（车站开关、线路允许集合多选 GUI、ESC 返回）完全不变。

| 环节 | 实现 |
|---|---|
| 客户端 | {@code TscDispatchClient}：JDK {@code HttpURLConnection}，全部在守护线程异步执行，绝不阻塞服务器主线程 |
| 拉取 | {@code TscDispatchBridge} 每 N 秒（默认 2）拉 {@code GET /v1/platforms?dimension} 与 {@code GET /v1/decisions?dimension&limit=50}；宽松解析，坏数据不抛异常 |
| 决策执行 | {@code PlatformDispatcher} 优先采用 tsc-dispatch 对该车的 {@code set_platform} 决策；{@code tsc_dispatch_required=true} 时**本地不再自行选台**，未连接时明确进入"等待 tsc-dispatch"状态 |
| 策略下发 | 每次保存车站/线路配置后，{@code TscDispatchExporter} 把允许集合导出为 tsc-dispatch 的 {@code platform_allow.rules} YAML 片段（路径可配） |
| 可见性 | 线路调度界面状态行显示 {@code tsc-dispatch 已连接（站台 N，决策 M）} / {@code 未连接}；连接建立时输出 INFO |

配置项（{@code config/mtrrealrail.properties}）：{@code tsc_dispatch_enabled}、{@code tsc_dispatch_url}（默认
{@code http://127.0.0.1:8787}）、{@code tsc_dispatch_poll_seconds}、{@code tsc_dispatch_required}、
{@code tsc_dispatch_dimension}、{@code tsc_dispatch_timeout_ms}、{@code tsc_dispatch_export_path}。

**联调实测**（真实 Forge 服务端 + tsc-dispatch 1.0.0 mock + run）：

```
tsc-dispatch: management api listening url=http://127.0.0.1:8787
tsc-dispatch: decision type=PLATFORM_SELECTION vehicle=1002 status=APPLIED executable=true
              reason="current platform already claimed by an earlier train"
```

## 4.7 经 tsc-dispatch 间接驱动执行桥 mtbridge（v1.4.0）

完整执行链：**本模组（交互/策略）→ tsc-dispatch（规划）→ mtbridge 2.0.1（执行）**。
tsc-dispatch 不直接改游戏，所有逐车动作（set_platform / deploy_train / return_to_depot / dwell_control）
都由它下发给执行桥 mtbridge，在服务器线程上落地。

| 环节 | 实现 |
|---|---|
| 桥发现 | TscDispatchBridge 探测 GET {bridge_url}/dispatch/v1/capabilities（带 Authorization: Bearer <token>），解析能力与 ready |
| 令牌 | 优先用 bridge_token 配置；留空则自动读取 mtbridge 的 config/mtbridge.json 的 token |
| 交给规划服务 | 自动 POST /v1/config 推送 bridge.base_url 与 bridge.auth_token（tsc-dispatch 的正确键名是 **auth_token**；bridge.token 会被拒绝为 unknown key） |
| 执行链门控 | execution_chain_required=true（默认）：链不完整时站台智能调度**待机**并给出明确状态，不再本地执行；链完整时选台与执行全部交给 tsc-dispatch→mtbridge，本模组只记录/展示 |
| 导出 | dispatch.generated.yml 同时包含 bridge（base_url/auth_token/mode）与 platform_allow 规则，可整段合并进 dispatch.yml |

**实测（真实 Forge 服务端 + mtbridge 2.0.1 + tsc-dispatch 1.0.0）**：

    [mtbridge] dispatch bridge loaded (127.0.0.1:8889, token enabled, dryRun false)
    [mtbridge] bridge listening on 127.0.0.1:8889
    本模组:    执行桥 mtbridge 已连接：http://127.0.0.1:8889（能力：set_platform,deploy_train,return_to_depot,dwell_control，ready=true）
    本模组:    已把执行桥地址与令牌推送给 tsc-dispatch：… {"applied":{"bridge.base_url":"…"},"rejected":{}}
    tsc-dispatch: control bridge detected url=http://127.0.0.1:8889 protocol=1 ready=true
                  features="[set_platform, deploy_train, return_to_depot, dwell_control]"
                  dimensions="[minecraft/overworld, minecraft/the_end, minecraft/the_nether]" actuator=bridge

启动顺序：① 服务器装 mtbridge + 本模组 → ② 起 tsc-dispatch（dispatch.yml 里 bridge.auth_token 与本模组导出的一致）→ ③ 游戏内在车站/线路界面配置允许站台。

## 4.8 解除"路径不可中途改写"限制 + 车厂在线路中间（v1.5.0）

### 4.8.1 限制解除：运行中的列车也能改停站台

原 §5.3(1) 的限制是"MTR 列车路径 immutablePath 在运行中不可替换，改停只能在路径生成阶段生效"。
现在改为**经执行链命令**实现：本模组判定需要改停时，下发
`POST /v1/command {"kind":"set_platform","vehicleId":"0x…","args":{"platform":"0x…"}}`
给 tsc-dispatch，由其转给 mtbridge；mtbridge 会对这辆车**重新生成进路**（`GameActions.regenerateTo`），
于是运行中的列车也能真正改停。为避免刷指令：同车 20 秒内最多一次；命令结果写入 tsc-dispatch 的决策日志与本模组日志。

### 4.8.2 新车厂开关：车厂在线路中间

位置：铁路仪表板 → 车厂 → **优化线路配置** 左列第 4 个开关「车厂在线路中间」。

| 行为 | 实现 |
|---|---|
| 开启后按最近路线驶向最近车站并投入运行 | 依据车厂时刻表的下一班（`Depot.getRealTimeDepartures()`）与提前量 `deployLeadMinutes`（默认 5 分钟），对车厂内停着的车辆下发 `deploy_train`（目标站台 = 该车厂线路上的车站站台），进路由 tsc-dispatch 规划、mtbridge 执行 |
| 无车发出的时段自行回场 | 距下一班超过 `idleReturnMinutes`（默认 30 分钟）或当日已无班次 → 对该车厂车辆下发 `return_to_depot` |
| 开启/关闭后自动清除车辆并刷新路线 | 切换时立即执行：按车厂名匹配侧线调用 `Siding.clearVehicles()` 清空车辆，再 `RouteRefresher.refreshDepot` 让 MTR 重新生成车厂路径；日志输出"清除车辆 N 辆，刷新路线 已请求" |
| 依赖 | 全部动作走 tsc-dispatch + mtbridge；`isChainActive()` 为假时**不动任何列车**（安全待机） |

配置持久化：`optimize.json` 每行追加 3 列（车厂在线路中间|提前派车|回场判定），
旧文件（9 列）自动兼容；GUI 与网络包同步新增字段。

### 5.3 已知限制（重要）

1. **列车路径（{@code immutablePath}）在运行中不可替换**（MTR 中是 final 且由车厂生成）：
   因此"改停其它站台"在**路径生成阶段**生效（通过 {@code RoutePlatformDataMixin} + 重新生成车厂路径），
   对已经生成的进路不会中途改写；运行中的列车通过"进站前等待"来避免堵死站台。
2. 站台识别采用"停车段端点 ∈ 站台"的判定（MTR 自身的 {@code Platform.containsPos} 语义），
   对超长站台/非常规布局可能识别不到，此时该列车不参与站台调度（安全降级，不影响行车）。
3. 车站/线路开关与允许集合以**存档**为单位保存；服务器替换 jar 后配置沿用。

## 6. 兼容性

- 仅依赖 {@code org.mtr.core} 的公开成员 + 3 个 MTR 自有方法名（{@code init2}、{@code writePlatformCache}），
  不含 MC 成员名，因此不需要 refmap；MTR 大版本升级时若改名，主配置会直接报错提示。
- 客户端两个界面 mixin 位于 {@code required=false} 配置（{@code mtrrealrail.railgui.mixins.json}），
  注入失败只记日志、不影响游戏；此时功能仍可通过服务端配置与命令式流程使用（只是没有界面入口）。
- 与其它 MTR 附属模组：本模组只改 {@code RoutePlatformData.platform} 缓存（MTR 每次生成路径都会重写该缓存），
  不修改线路数据本体，冲突面很小。
